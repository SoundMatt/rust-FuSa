# rust-FuSa Tool Safety Manual

**Version**: 0.2.6  
**Spec**: x-FuSa v1.10  
**Language**: Rust  
**Binary**: `rsfusa`

---

## 1. Purpose

rust-FuSa is a functional safety enablement toolkit for Rust projects. It provides static analysis, traceability, evidence generation, and CI integration to support certification activities under ISO 26262, IEC 61508, DO-178C, ISO 21434, IEC 62443, SLSA, and MISRA.

This document serves as the Tool Safety Manual required by ISO 26262-8 §11 for tool qualification. It describes the tool's intended use, limitations, validation evidence, and known anomalies.

## 2. Intended Use

rust-FuSa is intended to:

- Detect safety rule violations in Rust source code (FUSA, LINT, ANA, CYBER rule sets)
- Generate traceability matrices linking source code to safety requirements
- Produce evidence artefacts (SBOM, provenance, qualification report, audit pack) for certification submissions
- Support ASIL/SIL/DAL integrity level declarations and gap analysis against safety standards

rust-FuSa is **not** a certification product. Its output supports but does not replace the judgement of a qualified safety engineer.

## 3. Tool Classification (ISO 26262-8 §11.4)

| Attribute | Value |
|-----------|-------|
| Tool category | TCL-2 (tool with potential impact on functional safety) |
| Confidence level | TCI-2 |
| Qualification method | Validation (§11.4.5) |

## 4. Validation Evidence

All validation evidence is generated by `rsfusa qualify` and stored in `qualify-report.json`. The qualification suite:

- Covers all §9.1 MUST commands (positive and negative cases)
- Verifies correct exit codes for each finding severity
- Verifies JSON output conformance to x-FuSa spec §3.1
- Is deterministic: the qualify hash must match across clean rebuilds

Run `rsfusa qualify` to regenerate the qualification report. CI enforces this on every build.

## 5. Assumptions of Use

- The tool is run on a workstation or CI runner that has Rust 1.75+ installed
- The project under analysis is a Cargo workspace with a `Cargo.toml` at the root
- A `.fusa.json` configuration file is present declaring the target standard and integrity level
- The user reviews `check-report.json` and does not blindly suppress findings

## 6. Known Limitations

- Rules use text-based pattern matching, not full abstract syntax tree (AST) analysis
- False positives may occur in generated code; use `excludePaths` in `.fusa.json` to suppress
- `rsfusa coverage` requires either `cargo-tarpaulin` or `cargo-llvm-cov` to be installed
- `rsfusa vuln` requires `cargo-audit` for full CVE database access
- SARIF upload to GitHub Code Scanning requires `github/codeql-action` in CI

## 9. Exit Code Reference

| Code | Meaning |
|------|---------|
| 0 | Success — no gate-failing findings |
| 1 | Gate failure — ERROR findings (or WARNING with --strict) |
| 2 | Usage error — invalid arguments |
| 3 | Runtime error — I/O or parse failure |
